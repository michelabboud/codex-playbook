**Targets:** Codex Playbook `0bfac6cc762d5b4d2c2121df3678d4b3474f740e`; Claude Code Playbook `e5d218de2ec37e415b60457d0be69daed9efc8f0`

This note was written after the pinned repair diffs and the brief's required target files were read, and before any file under `docs/reviews/`, `docs/adr/`, or `docs/plans/` in either repository was opened. Repository content was read through pinned git objects. The current worktree was used only to load the mandatory local operating skills; because the proposed reviews skill is itself part of that instruction environment, this is a control and not proof of complete contextual blindness.

## Cold findings

1. **The admission predicate does not change when a batch starts.** Both rulebooks say a new batch may start while at most two closed batches are unruled, but neither defines “starts” or says that only one batch may be open on a line. At a count of two, a coordinator can admit N+2 and N+3 before either closes because both admissions observe the same count. The same omission lets later tasks be relabelled into an already-open batch unless rule 3.2's automatic close conditions or the planner's written cap are actively enforced. The twelve cases omit the decisive state “two closed, N+2 building, another batch proposed.” This appears blocking unless serial, non-overlapping batches are made explicit.

2. **The rule does not settle already-in-flight work when the third batch closes.** “Nothing new starts” stops future admission but does not say whether work already dispatched on the line may finish, land, or be accepted. Rule 3.3 gives that preservation-without-acceptance treatment for a returned blocker, but rule 3.5 does not import it for the ceiling. This is reachable through concurrent task dispatch or the undefined-start hole above.

3. **The merge boundary is incomplete.** A merge whose union exceeds three waits, but the text also calls conflict resolution new work and says nothing new starts on a line carrying three. The worked table has only “exceeds three”; it omits a merge proposed from a line already carrying exactly three whose union remains three. The intended answer is inferable but not normative.

4. **The twelve table rows otherwise agree between repositories and with the surrounding rule.** Rows 1–12 are semantically identical apart from the declared Codex mechanics. Rows 1–12 correctly cover normal pipelining, admission of the third batch, the stop at three, release after a ruling, set-union accounting, an over-three merge, mid-batch branching, ancestry-free copying, line-scoped fixes, an unsettled mechanical review at a gate, a returned mechanical blocker, and candidate freezing. The important omitted state is the second-open-batch admission described above; exact-three merge and already-in-flight work are secondary omissions.

5. **Pending versus returned is repaired in the operative text.** A pending mechanical review does not stall the next reversible task, while a returned blocker stops dependent dispatch and acceptance; row 11 reinforces that. The unqualified summaries “never waits” and “start the next task at once” remain broader than the detailed rule, but rule 3.5's three waits constrain expensive-to-undo dependent work, outward-facing or irreversible work, and known blockers. “Reversible” alone is too weak if those cross-references are read in isolation.

6. **The reviewer-isolation wording is satisfiable only when reach is actually constrained or the limitation is recorded.** The dedicated-parent condition fixes the literal filesystem-ancestry impossibility. It is not itself a sandbox: a reviewer may still be able to traverse from that parent to another review or programme material. The sentence about what the reviewer can reach plus the required limitation in the header can close that hole, but only if “cannot provide that” is applied to effective filesystem reach, not merely to the contents of the immediate parent.

7. **The assignment/selection boundary is materially repaired.** Numbered rules assign work and review tiers; each roster selects configurations, records the optional second family/binding, and carries evidence. The Codex roster names Claude only as measurement provenance, not in a tier assignment. I found no product identifier in the Codex tier assignments and no work-kind table left in either roster.

8. **The installer skips an unterminated final resource-inventory entry.** Validation accepts a syntactically valid final line without a newline, but `while IFS= read -r resource_path` does not execute its body for that line. A missing listed resource can therefore pass preflight and the whole-skill copy can install successfully without it. This violates the stated preflight contract before any backup or destination write and appears blocking.

9. **The resource check follows symlinked intermediate directories.** `[ -f "$resource_source" ] && [ ! -L "$resource_source" ]` rejects only a symlink at the final component. A `references` symlink to an external directory passes, and recursive copy preserves the symlink in the installed skill. Existing `SKILL.md` checks have the same limitation, but parity with an older check does not satisfy the new promise that managed resources are regular files inside the package. This appears blocking.

10. **A resource's owning skill need not be active.** The resource path grammar permits any syntactically valid `codex-playbook-*` directory and preflight checks the source file, but installation copies only active skills. A listed file under an inactive skill can be validated and then never installed. The pinned inventory does not trigger the defect because its only entry belongs to the active subagents skill, but the generalized inventory contract does not enforce its own relationship. Tentative severity: blocking because success can omit a declared installation dependency.

11. **The resource path grammar is otherwise conservative and portable.** It rejects absolute paths, traversal components, empty lines, carriage-return line endings, spaces, dotfiles, and components outside a managed-skill-shaped prefix. The extended regular expression uses POSIX constructs supported by GNU, BusyBox, and BSD `grep -E`. Rejecting names with spaces is a policy limitation, not a traversal hole. All new resource preflight runs before checkpoint creation or destination writes. `restore.sh` is unchanged; that is coherent because checkpoints and restoration operate on whole skill directories and do not consult the source inventory.

12. **The worked-case test is still a phrase-presence test, not a row contract.** It locks row numbers and one substring per row. A row can add a contradictory instruction (for example, “Do not Keep building”) and the test still passes while reporting that every case says what it must. Since the table is explicitly normative and a wrong row is blocking under the brief, the test should compare canonical complete rows or an equivalently strict structured representation.

13. **The new installer refusal tests prove only final-component absence/symlinking.** They correctly assert failure before a backup and unchanged destinations for those exact fixtures. They do not cover an intermediate-directory symlink, an unterminated final inventory line, or a resource under a non-active skill. The rulebook inventory test repeats the same final-component and unterminated-read weaknesses.

14. **No other pre-existing test assertion was removed in the repair diff.** The old rule-3.5 keyword accounting check was replaced by the numbered phrase checks and the admission/superseded-wording check; the old roster-table ownership check was replaced by the more specific tier-selection/no-known-assignment-shape check. The two installer tests are additions.

## Cold judgment on the rejected alternative

Rejecting “the third batch may be built but may not close” is correct. If its last planned task lands, the batch is closed as a matter of state; withholding the label or review would make the ledger less truthful without reducing exposure. Admission control is the right abstraction, but the current text needs to define admission/start and prohibit multiple simultaneously open batches on one line for the abstraction to enforce the stated three-range bound.
