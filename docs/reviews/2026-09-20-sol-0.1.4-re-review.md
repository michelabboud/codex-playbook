## Findings

### 1. Both repositories — Blocking — admission can be repeated before the count changes

**Target locations:** A `.agents/skills/codex-playbook-reviews/SKILL.md:45,53-54`; B `rules/REVIEWS.md:51,59-60`.

**Origin:** cold read.

The admission-rule abstraction is the right repair, and rejecting “build it but do not close it” was correct: once the last task lands, the batch is closed, and withholding its review only makes the ledger dishonest. The repair is nevertheless incomplete. “A new batch starts only while at most two closed batches are unruled” never defines *starts* and never says only one batch may be open on a line. Starting N+2 does not change the closed-batch count, so at a count of two the same coordinator can admit N+2 and N+3 before either closes. The stated three-range bound can then be exceeded without violating the literal admission predicate.

Rule 3.2 and planner-written caps prevent an obedient agent from keeping one batch open forever or silently stuffing work beyond its planned boundary. They do not close the concurrent-admission hole. The normative table makes the gap visible: row 2 permits N+2 to start, but there is no row for “N and N+1 closed and unruled; N+2 building; another batch proposed.” Nor does the rule say whether already-dispatched later work may finish, land, or be accepted when a third batch closes. “Nothing new starts” governs future dispatch only.

**Do instead:** define a batch start as the first dispatch or acceptance of work allocated to that planned batch; allow at most one open batch per line; prohibit dispatch into any later batch until the open batch closes and admission is re-evaluated; add the missing two-closed-plus-building row. If work was already dispatched when the line reaches three, preserve it but do not accept it onto the line until a ruling reduces the count, matching rule 3.3's treatment of in-flight dependent results. Also state the exact-three merge case: a merge proposed from a line already carrying three is new work and waits even when its union remains three.

### 2. A — Blocking — intermediate symlinks bypass managed-resource preflight

**Target locations:** `scripts/install.sh:219-224`; duplicated guard in `tests/rulebook_test.sh:379-385`.

**Origin:** cold read.

`[ -f "$resource_source" ] && [ ! -L "$resource_source" ]` rejects a symlink only at the final component. A source tree with `references` as a symlink to another directory passes when the external `roster.md` is regular. `cp -pR` then preserves that symlink in the installed managed skill, and the source/staging/destination directory comparisons can all agree on the unsafe payload. The installer can therefore replace a safe installed skill with one that resolves a required rulebook file outside the package while reporting success.

The existing `SKILL.md` check has the same final-component property. That is not acceptable parity: the new inventory's stated purpose is to refuse an incomplete or unsafe dependency before backup or destination writes.

**Do instead:** walk and `lstat` every component below the trusted package root, rejecting every symlink and non-directory intermediate component, then require a non-symlink regular leaf. Add an intermediate-directory-symlink fixture that asserts refusal before backup and unchanged destinations.

### 3. A — Blocking — an unterminated final inventory entry is never preflighted

**Target locations:** `scripts/install.sh:25-47,219-224`; same loop shape in `tests/rulebook_test.sh:358-385`.

**Origin:** cold read.

The regular expression, sorting, and duplicate checks accept a valid final line without a trailing newline. POSIX `read` assigns the bytes but returns failure at end-of-file, so the loop body does not run for that line. If that final entry names the missing roster, preflight skips it, whole-directory copy reproduces the absence, and installation can complete with the reviews skill pointing to nothing—the original blocking defect through a new edge case.

The pinned inventory does contain a final newline, so the held candidate itself is not presently in that malformed state. The installer claims to validate the inventory it is handed, and an incomplete checkout can reach this path.

**Do instead:** process the final entry with `while IFS= read -r resource_path || [ -n "$resource_path" ]; do ...; done`, or explicitly reject an unterminated inventory before iteration. Add a no-final-newline fixture with the listed resource absent.

### 4. A — Blocking — a resource may belong to a skill that installation never copies

**Target locations:** `scripts/install.sh:180-191,210-224,309-314`.

**Origin:** cold read.

The resource grammar accepts any `codex-playbook-*` package name. Preflight verifies that the source file exists, but never checks that the owning skill is in the active inventory. Installation copies only active skills. A damaged source can therefore list and successfully preflight a dependency under an inactive, retired, or entirely unmanaged skill, then report success without installing the declared dependency. In the most relevant form, removing `codex-playbook-subagents` from the active inventory leaves the reviews skill pointing at a sibling resource that was checked in the source and never installed.

The pinned roster entry currently belongs to an active skill; this is a missing invariant in the generalized inventory, not a claim that today's single line is mismatched.

**Do instead:** extract the owning skill from every resource path and require an exact membership match in `config/managed-skills.txt` before any backup. Add a refusal test for a real listed resource under a non-active skill.

## Other required judgments

### Pending versus returned

The operative text now distinguishes pending from returned correctly. A pending mechanical review does not stall the next reversible task; a returned blocker stops dependent dispatch and acceptance, and row 11 reinforces it. The table's “never waits” is under “while it runs,” so it reasonably describes pending status rather than a returned blocker. “Reversible” does not override the three explicit waits: expensive-to-undo dependent work, irreversible/outward-facing work, and work above a known blocker still wait. The canonical wording records that limitation and calls the controls non-proof, so I do not find a new rule defect. The two guides are stale as finding 6 describes.
