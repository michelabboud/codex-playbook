## Cold findings

### C1 — A and B — blocking — early closure has no disposition for already-dispatched work

A `.agents/skills/codex-playbook-reviews/SKILL.md:29,45,64-65`; B
`rules/REVIEWS.md:35,51,70-71`.

Rule 3.2 can close a batch before its planned last task, while rule 3.5 permits
multiple tasks in the one open batch to have been dispatched. The new text says
the batch closes early and its review is dispatched, but says what happens to an
already-dispatched later result only when that closure creates the third unruled
batch. At counts zero, one, or two, the later result was dispatched as part of the
now-closed batch, cannot enter that review's pinned target, and does not start a
new batch under the new definition because its first dispatch already happened.
It can therefore be accepted without belonging to any reviewed range, or must be
rejected by a rule that is not written.

Define batch membership at closure. The simplest safe rule is: closing freezes a
pinned target; every allocated result not reachable from that target is preserved
and must be reallocated to a newly admitted batch before it can land. Apply that
at every count, not only at three. Alternatively, forbid early closure until all
work allocated to the batch has returned, but that weakens rule 3.2 and is the
worse design.

### C2 — A and B — blocking — an open batch has no identity semantics after a branch split

A `.agents/skills/codex-playbook-reviews/SKILL.md:45-47`; B
`rules/REVIEWS.md:51-53`.

The ancestry rules define inheritance only for an *unruled* batch, which is
already closed. They do not define what happens if a line is cut after the first
task of an open batch is dispatched. Both descendants can continue work that the
plan allocated to the same open batch, but a ledger entry has one batch identity
and one base/target pair. If both close independently, one review target cannot
cover both; if they become separate batches, neither new batch necessarily had
its own first-dispatch admission check. “Batches that must run in parallel run on
separate lines” does not resolve a batch that becomes parallel after it starts.

Either prohibit splitting an open batch, or require the split to close/freeze the
old batch and admit distinct child batches on each line. Record the resulting
identities and pinned targets in the ledger.

### C3 — A — minor — the symlink scan does not inspect a symlinked package ancestor

A `scripts/install.sh:210-219`.

The final `skill_source` component is rejected when it is a symlink and `find`
rejects every symlink below it. A symlink at `.agents` or `.agents/skills`,
however, is followed while each final `skill_source` still appears to be a real
directory; `find` begins below the ancestor and never reports it. The installer
can then copy package content reached outside the checkout.

This cannot be represented by the pinned target's Git tree while that tree also
contains the skill descendants, so it is a hardening gap rather than a defect in
this target payload. If source preflight is meant to accept locally modified or
materialized checkouts as untrusted input, canonicalize and require every
package path to remain beneath a non-symlinked repository `.agents/skills`
directory, or explicitly validate those two ancestors.

## Cold analysis without a finding

- The sequential admission boundary is now explicit: one open batch per line,
  first dispatch starts it, closure forces a fresh admission check, and rows
  13-15 cover the double-start, in-flight-at-three, and merge-at-three cases.
- At three, “only work ... the fixes for its findings” plus “everything else
  waits” is a content restriction, not merely a label. A fix need not have an
  arbitrary size ceiling if validation re-reviews the amended batch, but any
  unrelated task bundled with it is not a fix and must wait. A final version
  would benefit from saying “only changes necessary to resolve a finding” so the
  exception cannot be gamed.
- Row 6 controls a fix delivered by merge: if the merge union exceeds three it
  waits, even if it contains a fix. The fix can be recreated or transplanted on
  the blocked line and then validated there. Row 16 is not an override of row 6.
- Parallel lines cut from a closed tip may each admit a batch from the same
  count. That creates unbounded repository-wide breadth, but no line exceeds
  three and their merge waits if its union exceeds three. The claimed three-range
  bound is therefore per line, not repository-wide; summaries should say so.
- Task-grain deep review for a risk-class task can be an extra review within the
  one open batch; it need not create another batch. A returned blocker still
  stops the line, and a high-deep gate still drains all lower reviews. The text
  is obeyable on this point, though “deep per batch” and “deep at task grain”
  require careful reading.
- A's new `find` and resource checks all occur before line 264, where the first
  destination creation begins. Under `set -eu`, a failing `find`, `cat`, or
  `grep` terminates or calls `die` before backup creation. Multiple symlink paths
  remain one quoted diagnostic argument.
- Inventory word splitting and globbing are safe because the already-run
  inventory validator admits only dot, slash, letters, digits, underscore and
  hyphen in the relevant positions; it admits no whitespace or shell glob
  metacharacters. Command substitution also preserves an unterminated final
  record's content. `grep -Fxq` matches an exact final line whether or not it has
  a trailing newline.
- Active skills are the only source directories copied. Retired skill sources
  are not a route to the destination. `AGENTS.md` and all three inventory leaves
  reject symlinks. A Git checkout does not preserve hard-link identity, and
  `cp -pR` materializes a regular destination file, so hard links do not create a
  destination traversal route. A symlink introduced after preflight is a
  time-of-check/time-of-use race; it is outside a pinned, quiescent checkout but
  must be closed by revalidating the staged copy if a concurrently mutable source
  is in scope.
- Each of the four new installer tests asserts the claimed diagnostic, absence of
  the backup root, and unchanged sentinels for `AGENTS.md`, the managed skill,
  and its nested resource. Their fixtures pass the earlier checks, so the named
  new check is the refusal cause.
- The worked-case test compares the header and all sixteen data rows byte for
  byte after removing indentation. The independent `1..16` sequence rejects a
  missing, duplicated, or reordered row. Dropping only the Markdown alignment
  row is sound because it carries presentation, not the normative state/action
  contract. A wrong row could pass only if the canonical fixture were changed to
  the same wrong text; that is the ordinary reviewed-test-oracle boundary, not
  the old one-phrase weakness.

## Cold judgment

The simple sequential path is repaired, but C1 leaves ordinary early-close
execution outside the ledger and C2 leaves an open batch undefined across a
branch. Those are state-machine holes in the law, so both rulebook candidates
remain unpublishable on the cold read. The installer delta is otherwise
coherent for a pinned, quiescent Git checkout.
