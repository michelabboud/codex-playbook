## Findings

### 1. Blocking — closing the active batch violates the stated ceiling

**Origin:** cold read; confirmed after reading the plan, ADR, and source.
**Target:** `.agents/skills/codex-playbook-reviews/SKILL.md:45`
**Source:** `rules/REVIEWS.md:51` at `checkpoint/0.1.14`
**Supporting target text:** `docs/guides/non-blocking-review-pipeline.md:122-135`

The rule says a line may carry at most two closed, unruled batches plus the one
being built. It then permits N+2 to build while N and N+1 are closed and unruled,
and says that when N+2 *closes* with those two still unruled the line waits. At
that instant there are three closed, unruled batches. Waiting before N+3 does not
repair the already-broken two-closed invariant.

The plan and ADR deliberately chose exposure of two closed batches plus one
active batch, but they never define the admission boundary when the active batch
is ready to close. State it explicitly: with two closed/unruled batches, N+2 may
be built but may not close or dispatch its deep review until one older batch is
ruled; no N+3 begins. If three closed batches are actually intended, rename the
ceiling and revise the exposure account.

This is a faithful direct port of the source text. Fidelity does not make the
instruction coherent; the same defect remains in source 0.1.14.

### 2. Blocking — a source checkout missing the roster can install successfully

**Origin:** after the cold read.
**Target:** `scripts/install.sh:203-210,295-299,333-338`
**Tests:** `tests/install_test.sh:377-393,861-929`
**Approved plan:** `docs/plans/2026-09-20-non-blocking-review-pipeline-port-plan.md:170`

Installer preflight requires each managed directory and its `SKILL.md`, but it
does not require the new nested roster. Staging and final verification compare a
skill directory to the source directory, so a source tree with the roster
missing copies that absence faithfully and passes those comparisons. The result
is an installed reviews skill that points to a missing prerequisite.

The generic incomplete-source test contains no skill tree and fails before it
can isolate this dependency. The three new nested-resource tests cover positive
upgrade/replacement/rollback behavior, not the approved missing-file case.

Require the roster to be a regular, non-symlink file during source preflight,
before backups or destination writes. Add a complete-source fixture with only
the roster removed and assert refusal plus zero destination changes.

### 3. Blocking — the approved accounting contract was replaced by keyword checks

**Origin:** cold-read concern; confirmed after reading the approved plan.
**Target:** `tests/rulebook_test.sh:295-301`
**Approved plan:** `docs/plans/2026-09-20-non-blocking-review-pipeline-port-plan.md:167`

The plan explicitly requires behavioral cases for merge union, a branch cut
inside a batch, and a missing mechanical review holding a gate, “not only
heading matches.” The implementation checks only that the reviews file contains
the words `union`, `plus the one being built`, and `mechanical included`, and
does not contain `merge adds`. It has no branch-cut case, missing-review case,
or state transition at the two-closed boundary. It passes while finding 1 is
present.

For prose law, textual assertions are useful but cannot prove interpretation.
Keyword presence is not adequate for the success message this test emits. Add a
normative scenario table with explicit inputs and allowed next actions, then
check every approved case: shared-ancestor union, mid-batch inheritance,
cherry-pick/manual identity, branch-specific fixes, failed or missing review
debt, gate drainage, and the ready-to-close transition at two outstanding
batches. Retain independent semantic review because even exact prose fixtures
cannot prove that an agent will interpret them correctly.

### 4. Blocking — “one owner” is contradicted by the consuming skills

**Origin:** cold read.
**Target:** `.agents/skills/codex-playbook-subagents/references/roster.md:3-7,14-19`
**Target:** `.agents/skills/codex-playbook-subagents/SKILL.md:12,14-16`
**Target:** `.agents/skills/codex-playbook-reviews/SKILL.md:18-27`
**Test:** `tests/rulebook_test.sh:277-286`

The roster and subagents entrypoint say the roster has one owner for the tier
definitions and that the entrypoint does not restate them. The entrypoint then
assigns Fast to mechanical implementation, Standard to multi-file work and
mechanical review, Strong to deep review, and Top to planning and risk-domain
work—the same responsibility definitions in the roster's `Trusted with` table.
The reviews skill repeats the review-to-tier assignments.

The test detects only literal Markdown rows beginning with `Top` or `Standard`.
It therefore reports one owner while equivalent normative prose exists in two
`SKILL.md` files.

Choose and state a precise boundary. Either the roster owns responsibilities and
the entrypoints refer to it without repeating assignments, or numbered rules own
the assignments and the roster owns only selection criteria, dated runtime
bindings, and evidence. Then make the test name that narrower structural
contract instead of claiming semantic single ownership from two grep patterns.

### 5. Blocking — mechanical review can both “never block” and stop the line

**Origin:** cold read; confirmed as a direct source carry-over.
**Target:** `.agents/skills/codex-playbook-reviews/SKILL.md:25,31-37,43`
**Source:** `rules/REVIEWS.md:31,37-43,49` at `checkpoint/0.1.14`

Rule 3.1 says a mechanical review “never blocks the next task.” Rules 3.3 and
3.5 say a blocking finding stops the line regardless of which kind of review
found it. The surrounding table suggests the intended distinction is *pending
review* versus *a returned blocker*, but the normative sentence itself does not
make that distinction. A literal agent can continue after a mechanical blocker
while citing rule 3.1.

Say: “A pending mechanical review never delays the next reversible task. Once
any review returns a blocking finding, stop-the-line applies regardless of
review kind.” Apply the same correction to the source if Direct parity is to be
retained.

### 6. Blocking — the scratch-directory ancestry requirement is not executable

**Origin:** cold read; confirmed in the source and guide.
**Target:** `.agents/skills/codex-playbook-reviews/SKILL.md:39`
**Source:** `rules/REVIEWS.md:45` at `checkpoint/0.1.14`
**Guide:** `docs/guides/non-blocking-review-pipeline.md:209-226`

The rule requires each reviewer to have a scratch directory with no other
reviewer and no programme material “anywhere above it.” Every ordinary path has
parents through the filesystem root, and a Codex lane generally cannot inspect,
control, or prove that property across the entire ancestry. The instruction is
therefore impossible to satisfy literally under the sandbox model the same rule
describes.

Scope the condition to the reviewer-visible or task-managed workspace subtree.
Require a dedicated parent with enumerated contents when the runtime can provide
one, and require the review header to record when stronger filesystem isolation
was unavailable.
