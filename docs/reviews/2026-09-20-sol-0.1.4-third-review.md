## Findings

### 1. Both repositories — Blocking — early closure strands already-dispatched work outside every batch target

**Target locations:** A `.agents/skills/codex-playbook-reviews/SKILL.md:29,45,64-65`;
B `rules/REVIEWS.md:35,51,70-71`.

**Origin:** cold read.

Rule 3.2 can close a batch before its planned last task. The new rule also permits
multiple tasks allocated to the one open batch to be in flight. Closure freezes
and dispatches a review, but the text deals with a later dispatched result only
when that closure creates the third unruled batch. At counts zero, one, or two,
the result was dispatched as part of a batch that is now closed, is not reachable
from that review's pinned target, and cannot start a new batch under the new
definition because its first dispatch already happened. The law therefore lets
it land without a review debt, or requires it to wait under a rule that does not
exist.

**Do instead:** closing a batch must freeze its membership and pinned target at
every count. Any allocated result not reachable from that target is preserved
but must be reallocated to a newly admitted batch before it can land. Do not
special-case this only at three.

### 2. Both repositories — Blocking — an open batch has no inheritance or identity rule when its line branches

**Target locations:** A `.agents/skills/codex-playbook-reviews/SKILL.md:45-47`;
B `rules/REVIEWS.md:51-53`.

**Origin:** cold read.

The ancestry rule carries only *unruled* batches, which are already closed. If a
branch is cut after an open batch's first dispatch, the child can appear to have
no open batch and admit another one, while the parent continues the first. Or
both descendants can continue tasks allocated to the same batch and close at
different, incomparable targets. A single batch identity and pinned review
target cannot cover both states. “Parallel batches run on separate lines” does
not say whether an already-open batch is inherited, split, or frozen.

**Do instead:** prohibit branching an open batch, or make the split close and
freeze the old batch and require distinct, admitted child batches on each line.
The ledger must record the resulting identities and review targets.

### 3. B — Minor — the held target's handoff still claims completion

**Target location:** `HANDOFF.md:3`.

**Origin:** post-read; re-check of earlier finding 9.

The previous validator dismissed this because the file would become true once
published. That reason does not hold. A handoff describes the repository state
for local coordinators and reviewers as well as future public readers. At the
pinned, explicitly held target, review is active, there is no checkpoint tag,
and this review finds blockers. “No session is mid-work. v0.1.15 is complete” is
false now; a future publication cannot retroactively make the review input
truthful.

**Do instead:** state that v0.1.15 is held in review at the pinned target and
unpublished. Change it to complete only in the publication closeout commit.

### 4. Both repositories — Minor — public summaries substitute “unreviewed” for the rule's “unruled” state

**Target locations:** A `README.md:36`, `docs/index.html:292`; B `README.md:150`,
`docs/index.html:404`.

**Origin:** post-read carrier audit.

The rule counts a closed batch until every finding is validated and every blocker
is fixed or dismissed. A review that has returned but has unresolved findings is
reviewed and still unruled. The public carriers say the ceiling counts
“unreviewed” batches, which can tell a reader that a returned review releases a
slot. B's authority summary and both canonical rules use the correct word.

**Do instead:** use “unruled” in the summaries and define it briefly where the
reader does not have the canonical rule beside it.

### 5. A — Minor — a symlinked package ancestor remains outside the source scan

**Target location:** `scripts/install.sh:210-219`.

**Origin:** cold read.

The final `skill_source` component is rejected when it is a symlink, and `find`
rejects every symlink below it. A symlink at `.agents` or `.agents/skills` is an
ancestor of the scan root: each final skill path can still appear to be a real
directory, and `find` never reports the ancestor. The payload can then be copied
from outside the checkout.

The pinned Git tree cannot represent such an ancestor symlink while also
containing the tracked descendants, so this is a hardening gap rather than a
defect in the pinned payload.

**Do instead:** if locally materialized checkouts are part of the preflight
threat model, reject symlinks in the repository-owned `.agents` and
`.agents/skills` ancestors or prove each skill's canonical path stays under a
canonical non-symlink package root.

### 6. A — Minor — the repair's own records retain two stale counts

**Target locations:** `PROGRESS.md:28-31`; `CHANGELOG.md:67-75`.

**Origin:** post-read carrier audit.

`PROGRESS.md` says the lifecycle coverage has “the two refusals” although the
suite now carries the two earlier resource refusals plus four new ones. The
changelog says the candidate was reviewed twice by the other family while the
same target records the third re-review that produced this delta. Neither changes
the rule, but both misdescribe the evidence behind the candidate.

**Do instead:** say six source-resource refusal scenarios, or avoid a count; say
three independent reviews and distinguish the plan review, first candidate
review, and repair re-review.

## Rule 3.5 audit

Rows 13-16 are locally correct on a sequential line:

- row 13 closes the repeated-admission hole while N+2 is open;
- row 14 preserves but does not accept a later result when the third batch closes;
- row 15 correctly treats an exact-three merge without a fix as new work; and
- row 16 correctly permits repair work needed to bring the count down.

The three-range bound is nevertheless not enforced over all states because
findings 1 and 2 leave work without an admitted batch identity. Parallel lines
cut from a *closed* tip may each open a batch; that deliberately creates more
than three ranges repository-wide, but each line stays at three and a union over
three cannot merge. The rule's bound is per line, not global, and carriers should
say that when they use “honest worst case.”

The fix exception is not itself a blocker. “Only work ... the fixes for its
findings” followed by “everything else waits” excludes a new task disguised in
the same change. A numeric size limit would be artificial: a necessary repair
can be large, but must remain attached to and revalidated with the batch it
repairs. The text would be harder to game if it said “only changes necessary to
resolve a recorded finding.” A merge containing a fix does not override row 6:
if its ancestry union exceeds three, it waits and the fix must be recreated or
transplanted onto the blocked line.

One open batch does not inherently conflict with task-grain risk review. A
security, concurrency, data, unsafe-code, or public-API task can receive an extra
deep review within its planned batch; a returned blocker still stops the line.
Nor does it conflict with a high-deep gate, which first drains every lower review
and freezes the candidate. The text is demanding but coherent in those states.

It is now too intricate to repair safely with another prose clause and rows
17-18. The same boundary has failed repeatedly, and the two new omissions are a
consequence of counting only *closed* batches while admission, branching, and
acceptance act on open work. Replace it with one state invariant: **a line may
carry at most three admitted, not-yet-ruled batch identities, including its at
most one open batch**. Opening reserves an identity; closing changes its state
but not the count; repairs remain attached to an existing identity; no other
work lands at three. Then define early-close leftovers and branch splits once.
That is simpler to obey and preserves the intended three-range exposure.

## Installer audit

The three changed checks are before any backup or destination write. Source
preflight ends at `scripts/install.sh:232`; the first destination creation is
`mkdir -p "$codex_home"` at line 265.

- Under `set -eu`, `skill_symlinks=$(find ...)` has the exit status of `find`; a
  `find` error exits before the backup. Multiple paths stay in one quoted
  diagnostic argument.
- `managed_resource_paths=$(cat ...)` preserves an unterminated final record's
  content. The `for` is safe after `validate_inventory`: the grammar admits no
  whitespace or glob metacharacters, so word splitting separates only records
  and pathname expansion has nothing to expand.
- `${resource_path#.agents/skills/}` and `${resource_owner%%/*}` are defined for
  every path the validated grammar admits. `grep -Fxq` matches an exact last
  active-skill line with or without a final newline. A read error fails before a
  backup rather than silently authorizing membership.
- Active skill directories are the only source packages copied. Retired skills
  are checkpointed/removed at the destination but no retired source payload can
  enter. `AGENTS.md` rejects a symlink leaf. All three inventories reject
  symlink leaves before use. A hard link is not preserved by Git and the copy
  materializes ordinary destination content, so it is not a path-traversal route
  from a checkout.
- A symlink created between preflight and copy is a time-of-check/time-of-use
  race. It is outside a pinned, quiescent checkout. If a concurrently mutable or
  hostile source is in scope, the installer must snapshot/lock the source or
  revalidate the staged tree before activation; the current scan does not defend
  that threat model.

Apart from finding 5 and the explicitly excluded concurrent-mutation model, no
route remains for a symlink to enter the installed active skill payload.
