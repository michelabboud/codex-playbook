## Findings (most severe first)

### 1. Minor — the "no superseded wording" pass/fail messages say "rule 3.5" but the sweep covers rules 3.1 and 3.3 too

`tests/rulebook_test.sh:379` (pass) and `:381` (fail). The pass line reads `the reviews skill contains no superseded rule 3.5 wording`. Of the six forbidden sentences, at least `never blocks the next task` is old rule 3.1 wording (it is in `fd3de7a`, the original modular rulebook, and in `0bfac6c`). The brief says a second and third were 3.1/3.3 wording; I confirmed only the first from history, because `git log -S` gave no clean origin for `anywhere above it` or `merge adds` (see "could not verify"). A maintainer reading the passing output is told the sweep guards rule 3.5 only, when it deliberately guards the whole skill.

Instead: `the reviews skill contains none of the six superseded sentences (rules 3.1, 3.3, 3.5)`. The fail message could stay as is; its subject is already "the reviews skill".

### 2. Minor — both failure messages list every phrase rather than the one that is wrong

`tests/rulebook_test.sh:370` and `:381`. Each check is one `&&` chain, and one `fail` prints all eight required (or all six forbidden) sentences. I mutated a scratch copy so that exactly one phrase was missing or misplaced:

- M1: moved `Only closed work merges between lines` out of 3.5 into the "Dual review" paragraph (outside 3.5).
- M2: changed `the row wins` in 3.5.

Both took the suite from 52 to 51 passes, with one FAIL line naming all eight phrases. The maintainer has to grep eight strings to find the culprit. The forbidden-sentence check (M3, M4) has the same shape and does not say which sentence matched or where.

Wording is fine, and the message correctly says "rule 3.5 itself", so the maintainer knows where to look. This is a usability gap and not a behaviour gap. Instead: loop over the phrases and print the missing one (or the matching forbidden one with `grep -n`). That is a few lines and would make the "inside rule 3.5" locality visible.
