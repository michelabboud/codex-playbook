# 3 · Code reviews — rules 3.1–3.5

*Local layer: if `playbook-local.md` exists in the Codex home, its entries apply only within the non-authorizing, never-weaken boundary in (`AGENTS.md`, "The local layer").*

*Read when a task lands, at a batch boundary, before a milestone or release, and before dispatching any reviewer. What a review may NOT do is in the classification table and rule 7.4 (read, report, never fix); this file is what a review MUST do, who does it, and when. The record is the persisted review with its CONFIRMED / REFUTED / UNVERIFIED header. **This skill names roles, never models.***

**The roster — read it before assigning a reviewer.** **This skill owns the assignments** — which review runs on which tier (rule 3.1). **What each tier *is*** — how a Top, Strong, Standard or Fast configuration is selected — the optional second family, the operator's binding and the measurement behind the mechanical-review floor have one owner: `../codex-playbook-subagents/references/roster.md`. Resolve that path from the directory containing this `SKILL.md`, not from the project's working directory, so the roster packaged alongside this skill is the one you read. If it is missing or unreadable, report the missing prerequisite before assigning a reviewer; if your client will not follow a reference into a sibling skill, invoke `codex-playbook-subagents`, which reads its own copy. Never restate the roster here.

**Why this shape:** a dual review after every task — one mechanical, one deep — is the right instinct, but on a big project it slows development dramatically. Mechanical reviews are slow; deep reviews are slow *and* expensive; and a review that development sits waiting for is a stall either way. So: development does not wait for a review unless waiting is cheaper than the rework — rule 3.5 says exactly when — and the deep review is batched every 3 to 10 tasks depending on complexity, with the coordinator or the plan's author deciding. At the end, regardless of task count, run the best review available. Split the tiers so expensive reasoning is not spent on overkill. The cost of a review is mostly the reviewer reloading the codebase; batching pays that once. The cost of a *late* review is rework on everything built on top of the defect; dependencies, not counts, bound the batch.

3.1 **Three kinds of review — and a tier that climbs the ladder.** The planner plans in levels (the vocabulary defined by `codex-playbook-workflow`) and each level closes with a stronger review than the one below it:

    | Level | What closes it | Review | Who (what each tier is: the roster reference) | While it runs, development… | Tag |
    |---|---|---|---|---|---|
    | **task** | one unit of work, rules 6.1–6.2 | mechanical | Standard tier; coordinator validates | never waits | `checkpoint/<VERSION>` |
    | **batch** | 3–10 tasks, boundaries in the plan | deep | Strong tier; coordinator validates, Top tier on request | keeps going, up to the ceiling (rule 3.5) | `gate/<VERSION>` on the tip presented |
    | **milestone** | something real shown working end to end | high deep — deep + plan conformance: the planner re-reads the plan against reality and revises it here | Top tier, dual-blind | waits (rule 3.5) | `gate/<VERSION>` |
    | **phase → release** | the phase's last task, rule 6.3 chain | high deep — the best review, rule 3.4 | Top tier, dual-blind, fed every review below it | waits | `v<VERSION>` — never before it passes |

    Levels collapse when the plan is small; the tier of the level that closes never drops.

    - **Mechanical** — tests and lint actually run, input handling, ignored return values, obvious defects, conformance to the brief. **Per task**, on the Standard tier and never the Fast one (a conservative floor — see the roster reference for the measurement and its limits), findings validated by the **coordinator**, not the planner. **A pending mechanical review never delays the next reversible task; once any review returns a blocking finding, stop-the-line applies, whatever kind of review found it** (rule 3.3).
    - **Deep** — architecture, concurrency, security, data paths, whether the code still matches the approved plan. **Per batch** of 3–10 tasks by complexity; the **planner writes the batch boundaries into the plan** so nobody decides them under pressure. On the Strong tier, **pipelined** with development (rules 3.3 and 3.5).
    - **High deep** — everything a deep review does, plus the plan itself re-read against reality. **Per milestone and per release**, on the Top tier, dual-blind, with every finding validated against source. It is a **gate**: a deep review looks for defects, whose cost the ceiling in rule 3.5 bounds; a high deep review may *revise the plan*, and work done past it risks being built against a plan that is about to change — no ceiling bounds that.

3.2 **A batch closes at whichever comes first:** (a) the next task would build on unreviewed work it cannot cheaply undo; (b) the diff has outgrown what one reviewer can hold — the human-review literature puts the cliff at a few hundred changed lines, and models dilute the same way, only later; (c) the planner's cap. **Risk overrides cadence:** security, concurrency, data safety, unsafe code, and public-API tasks get the deep review at task grain, always — the cadence rule never undoes rule 8.1's list.

3.3 **Pipelined, never fire-and-forget.** Review batch N while batch N+1 builds. Every finding pins the commit it was found on and is **re-checked against the current tip** before anyone acts on it. A blocker finding **stops the line** — no further dispatch on top of it until it is ruled. "Non-blocking" without the stop is building on known-bad foundations for a day.

    **How to pipeline, concretely** — each line is a way the pipeline fails *silently* if you skip it:

    - **A review's input is a commit, never a working tree.** Commit the work, dispatch the reviewer against that sha — **the full target commit and, for a change review, its base; a moving branch name is not a pin** — and start the next task at once. Do not sit waiting on it: **register how completion is signalled** — the runtime's event or wait facility, bounded status checks only when nothing better exists — and handle completion, failure, timeout and interruption. If the reviewer's input is "the current state of the repo", review and development are one process and one of them must wait. The commonest failure is pipelining the dispatch and then waiting for the result anyway, because the review feels important: the pipeline's shape with none of its benefit.
    - **The brief says: read git objects only — `git show <sha>:<path>`, `git diff <a>..<b>`, `git ls-tree`, `git grep <pattern> <sha>` — and never the working tree, because other lanes are using it.** A reviewer that reads the working tree sees the half-written next task and reports defects that do not exist in what it was asked to review. A reviewer that must **build or run tests** does it in a **detached worktree of that sha, in its own scratch directory, with its own build-output directory** — never in the shared tree. That costs disk and a cold build; sharing the build directory instead makes it contend for locks with the lane that is developing. **Whoever holds the permission prepares that snapshot:** creating a worktree needs write access to the filesystem *and* to git metadata, and neither the reviewer nor the coordinator has it merely because a brief says so. **Review-only is an authority; read-only is a filesystem.** Command subprocesses, git included, inherit the sandbox, and some sandboxes protect git metadata even inside a writable root — so this is a capability check, not an assumed escape hatch. A reviewer whose sandbox or permission profile cannot write returns its cold-read note and its findings through its reply, marks the checks it could not run as *unavailable*, and the required checks go to a lane already authorized to run them. **Never widen a reviewer's permissions to make the rule look satisfied.**
    - **The brief defines what counts as blocking**, or "non-blocking" means nothing. *Blocking:* a behaviour change nobody asked for, a lost safeguard or cleanup, a weakened limit, a security or data decision reachable a new way, or any defect the next tasks will build on. *Minor:* documentation or comments that misdescribe the code — nothing that changes behaviour. *Informational:* everything else. Blocking stops the line; the other two queue. **Stopping the line** means no new dependent dispatch *and* no acceptance of dependent results already running — their work is preserved, never killed — while work shown to be independent continues. **A finding's impact decides, never the kind of review that found it:** an unenforced input limit is a mechanical finding and can be a security defect.
    - **The coordinator commits the reviewer's output the moment its findings are complete** — the coordinator, never the reviewer (a review is read-only), **committing that one path and nothing else: check the index first, because anything already staged rides along** (`git commit -- <path>`, after confirming nothing else is staged). The working tree holds someone's half-written task. **An exited reviewer is not an accepted review:** one that died, timed out or returned empty is still owed, and a retry keeps the original target or says plainly that it supersedes it. Capture with it the target and base, the completion status, and the reviewer's actual model and effort where the runtime exposes them. The record is then provably the reviewed version, not whatever the file became later.
    - **A child agent or thread that shares the coordinating session's history does not count as blind** — not to its siblings, and not to the session that spawned it. A prompt that says "use this directory" enforces nothing: where children share the workspace and inherit history, no brief, path exclusion or directory layout controls what they know. (In the source rulebook's evidence, context crossed a session-to-subagent boundary in both directions on another client. Nothing is asserted here about this client beyond: **record what isolation the runtime actually provides.**) The second reviewer of a dual-blind pair is a **separate process with a fresh context** — the approved brief and inputs only, no implementation discussion, no other reviewer's findings. **A child that inherits the coordinating session's conversation — a full-history fork included — is never a blind reviewer.** The instruction environment is an input too: global rules, skills, memory and hooks reach a reviewer without being in its brief, so record their versions where it matters, and when the rulebook itself is under review, the proposed rules are the subject, never the authority. Each blind reviewer writes a **cold-read note to disk after reading its brief and the material under review, and before it opens anything else** — other reviews, the coordinator's documents, any adjudication — and only the findings in that note count as independent corroboration; whatever it adds later is an ordinary finding. **These are controls, not proof:** a separate process can be handed contaminated inputs, and a note preserves what the reviewer wrote, not everything it knew. Record what isolation the runtime actually provided, and claim no more than that. Enumerate the excluded paths rather than describing them, and give each reviewer a **dedicated scratch directory whose parent holds nothing but that reviewer's own material** — no other reviewer, no programme documents — within the workspace the task manages; every path has the filesystem root above it, so the condition is about what the reviewer can reach, not about the whole ancestry. Where the runtime cannot provide that, the review header says so.

3.4 **The release gate gets the best review, regardless of task count.** High deep: use the Top tier for two independent passes, give both the plan and every batch review, and direct them first to risk-class files rather than making them read the whole diff cold. Every finding is validated against source before it reaches me. No `v*` tag before it passes (rule 6.3).

3.5 **How far development may run ahead of review**. The test is never what the review costs; it is what being wrong costs. Most of what a mechanical review finds is local — fixing it three tasks later costs what fixing it now would — so waiting for a routine mechanical review costs more than it saves, and mechanical review has no ceiling of its own. **What a finding stops is decided by its impact, never by the kind of review that found it** (rule 3.3). A deep finding is structural, and its fix grows with everything built on top of it, so deep review has a ceiling:

    - **The ceiling is one invariant: a line carries at most three unruled batches, the open one included**. A batch is *unruled* from the moment it is admitted until it is ruled, and it passes through three states. **Admitted — open:** at the first dispatch of a task that belongs to it, and only when the line has no open batch and carries at most two unruled ones. Planned work opens the batch the plan allocates it to. Authorized work that needs no plan — a hotfix, a docs correction — opens an **ad-hoc batch** that the coordinator names in the ledger, owing the same reviews; that is bookkeeping, never a new approval. One batch is open per line at a time; batches that must run in parallel run on separate lines, which the merge rule below bounds. **Closed:** when its last task lands, or earlier when rule 3.2 closes it. Closing pins the review target, freezes the batch's membership and dispatches its deep review at once; a task that belonged to it whose result is not reachable from that target may finish, but its result belongs to the *next* batch — preserved, and accepted onto the line only once that batch is admitted (rule 3.3 treats in-flight work the same way). Closing changes a batch's state, never the count. **Ruled:** when every finding is validated and every blocker fixed or dismissed with a reason — and, where fixes landed, when a focused review of the pinned target plus its fix commits, at the depth of the review that found the defect, has returned and been validated like any other (rule 3.3). The pinned target stays as pinned; the ledger records each fix commit. A ruling is the only thing that brings the count down. **Every landing belongs to the line's open batch, with one exception: the fix for a recorded finding**, which attaches to the unruled batch it repairs — only the changes necessary to resolve that finding. Two is the normal state: batch N is in review while batch N+1 builds. Three — N and N+1 in review, N+2 open — is allowed and **announced loudly** because it means the review lane is in trouble: a slow reviewer, an exhausted allowance, a dead lane. The point of the third slot is that a review outage does not become a development outage. When N+2 closes the count is still three: all three reviews run, no batch can be admitted, and the only work the line accepts is what rules a batch — development waits, or moves to work outside the chain. **The honest worst case is therefore three batch ranges of unreviewed code per line**, so **the planner runs smaller batches whenever two are outstanding**: batch size is the real knob.
    - **Counted per line of work, by ancestry — as a set**. A line's count is the set of unruled batches with **any commit reachable from its tip**. Independent branches and worktrees never affect each other's count. **A task's own worktree is not a line:** its result lands on the line it was dispatched from, as part of that line's open batch. A line of work started from unreviewed work — even from the middle of a batch, an open one included — **inherits** it as it stood at the cut; the batch stays with the line that opened it, and work on the new line is a new batch, admitted there against the inherited count. After a **merge the count is the union** reachable from the merge commit, never the sum: a shared unruled ancestor counts once. A merge whose union would exceed **three** unruled batches **waits** — otherwise fanning out into worktrees and merging back is a way around the ceiling — and the merge result is itself new work: a conflict resolution can hold a defect neither parent had, so it belongs to the destination's open batch like any other landing. **Only closed work merges between lines:** a merge from a line whose batch is still open waits until that batch closes — an open batch has no pinned target, so the destination could not say which review covers what it took in. **Ancestry cannot see cherry-picks, squashes or copied code:** carry the batch's identity across by hand, or treat the copy as new work owing its own review. **A ruling clears a line only when its fixes are reachable from that line** — a blocker fixed on one branch is still open on another. A reviewer's detached worktree holds no development and counts for nothing.
    - **The coordinator keeps the ledger, and one coordinator admits work.** Git knows ancestry; it does not know which commits form a batch, which reviews are owed, or whether one was ruled. The ledger records, per batch and per review: identity, kind, base and target commits, status (queued · running · failed · returned · ruled), each finding's disposition, the fix commits, and the lines the ruling applies to. Dispatching a review releases nothing, and neither does its process exiting. Two coordinators admitting work from the same stale count can exceed the ceiling with correct arithmetic — so one owns admission per repository, and the ledger travels in the handoff. A table in the plan is enough.
    - **What this rule does not name is resolved toward review.** A state that no sentence and no row covers is not a loophole: the work counts as unruled, belongs to a new batch, and waits if the line is at three. The coordinator records the case in the ledger, and the rule is amended from the record.
    - **Worked cases — normative.** When the prose above and a row below seem to disagree, the row wins and the prose is a defect to report.

        | # | State of the line | What may happen next |
        |---|---|---|
        | 1 | N closed and unruled; N+1 building | Normal. Keep building. |
        | 2 | N and N+1 closed and unruled | N+2 may start — announced loudly: the review lane is in trouble. |
        | 3 | N and N+1 closed and unruled; N+2's last task lands | N+2 closes and its deep review is dispatched — three closed and unruled. **No new batch starts** until one is ruled. |
        | 4 | Three closed and unruled; N is then ruled | Two remain. N+3 may start. |
        | 5 | Lines X and Y both inherit unruled A; Y also carries unruled B; they merge | The merged line carries `{A, B}` — two, not three. |
        | 6 | The union after a merge would exceed three unruled batches | The merge waits until enough are ruled. |
        | 7 | A line of work is cut from the middle of batch A, open or in review | It inherits A as it stood at the cut and starts at one. A stays the batch of the line that opened it; work on the new line is a new batch, admitted there. |
        | 8 | Commits of unruled A are cherry-picked or squashed onto line Z | Ancestry does not show it. Record A against Z in the ledger, or treat the copy as new work owing its own review. |
        | 9 | A's blocker is fixed on line X and the fix's focused review is validated; line Y also carries A | A is ruled for X only. Y carries it until the fix is reachable from Y. |
        | 10 | A milestone is reached; one task's mechanical review died or timed out | The gate does not start. The review is re-run, or explicitly superseded. |
        | 11 | A mechanical review returns a blocking finding | Stop the line, exactly as for a deep review's blocker. |
        | 12 | A gate is running; a docs fix is ready | It lands on a line not merged into the candidate, in a batch admitted there — ad-hoc if the plan has none — owing its normal reviews. Merging it restarts the candidate's checks and review. |
        | 13 | N and N+1 in review; N+2 open; another batch is proposed | It waits: the line already carries three, and one batch is open per line. |
        | 14 | Rule 3.2 closes a batch early while a task allocated to it is still running — at any count | The task may finish. Its result belongs to the next batch: preserved, and accepted only once that batch is admitted. |
        | 15 | Three unruled, none open; a merge that carries no fix is proposed, and its union stays three | The merge waits: nothing lands outside a batch, and none can be admitted. |
        | 16 | Three unruled, none open; the fix for N's blocker is ready | It lands, attached to N: only the changes necessary to resolve the recorded finding. N is ruled once a focused review of N's pinned target plus its fixes is validated. |
        | 17 | A task of open batch A runs in its own worktree | That worktree is not a line. Its result lands on the line it was dispatched from, as part of A. |
        | 18 | An authorized hotfix or docs correction that no plan covers is ready | With a batch open, it belongs to that batch. With none open and at most two unruled, the coordinator names an ad-hoc batch in the ledger and admits it — same reviews owed, no new approval. At three, it waits unless it is the fix for a recorded finding. |
        | 19 | Line Y's batch B is still open; Y is proposed for merge into X | The merge waits until B closes: an open batch has no pinned target. |
        | 20 | A state that no sentence and no row covers | Resolved toward review: the work counts as unruled, belongs to a new batch, and waits at three. Record the case in the ledger. |
    - **Three waits hold at any depth:** (1) the next work builds on the unreviewed batch in a way that is expensive to undo — a storage schema, a public API, a protocol — and then only the *dependent* tasks wait; (2) anything irreversible or outward-facing — a migration on real data, a publish, a deploy, a release tag — never runs ahead of its review; (3) a blocker in any outstanding batch stops everything built on top of it (rule 3.3).
    - **High deep reviews are gates, and every lower review is settled first — mechanical included.** A high deep review takes the reviews below it as inputs, so every one owed for its scope has a final disposition before it starts; a review that is missing, dead, timed out or empty is still owed. So **the count drains to zero at every milestone**, and unreviewed work never survives past one. **The candidate is frozen while the gate runs.** The wait has work to do — the queued minor findings, the backlog, test hardening, docs — but on a line that is **not merged into the candidate until the gate passes**; anything that changes the candidate needs its checks and its review again. Where the documentation *is* the product, as in a rulebook, docs are not "independent work".
    - **The planner owns the stall.** If everything in batch N+1 depends on batch N, no review rule can keep development moving — the plan forced the wait. The planner puts independent work after every batch boundary, and puts risk-class tasks *early* in a batch, so their task-grain deep review finishes while the rest of the batch builds.
    - **Review capacity is shared even though the counts are not — and it is not host load.** Every line draws on the same reviewers, the same token allowance and the same host; rule 8.1's concurrency cap measures the host, not a remote model's allowance, so reviewer capacity is budgeted separately and enough of it is reserved that development cannot starve its own safety net. Never raise the ceiling to hide a starved review lane. When the review lane is down, every line reaches its ceiling together — report that once, as one fact, not once per line.

**Dual review, and why it must be decorrelated.** Two reviewers are worth more than one only if they can fail differently. Run them **blind to each other** — each assesses independently, and they compare afterwards; blind means separate processes and a cold-read note first (rule 3.3). Where your setup offers more than one model family, put the second pass on a different one (the roster reference's optional second family); where none is reachable, the pair is two fresh same-family sessions and the review header records that limitation; two instances of the same model share the same blind spots, and agreeing with yourself is not corroboration. A review that corrects a review can itself be wrong, so disagreement between reviewers is a finding to verify and rule on, never to average.

**Mechanics that do not change:** a review is read-only (classification table); defects found are fixed in their own commit after the review or deferred loudly (rule 7.4); reviewer ≠ worker; reviewers assess independently before they compare.

**A note on dependent work.** If your coordinator gates a dependent task on an *accepted* prerequisite, and accepted means reviewed, that forbids batching a dependent chain — and pipelining one. Either give the coordinator a provisional state — checks passed, review pending — or declare in the plan that a batch may span dependents. Until one of those exists, batching and pipelining cover independent tasks only.

**Measured, not assumed:** record in the close-out the tokens per review where the runtime supplies them ("unavailable" otherwise), the queue time and latency of each review, the defects found per review, and **how often a line carried three unruled batches, and how often a batch was admitted with two already carried** — so the 3–10 window and the ceiling of three get numbers behind them rather than preferences. A ceiling that is never reached does not matter; one that is reached often means the review lane needs fixing, not the ceiling raising.
