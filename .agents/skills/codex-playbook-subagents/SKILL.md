# 8 · Subagents & model tiering — rule 8.1

*Local layer: if `playbook-local.md` exists in the Codex home, its entries apply only within the non-authorizing, never-weaken boundary in (`AGENTS.md`, "The local layer").*

*Read before dispatching any subagent or planning a fan-out.*

*For supported multi-agent execution, messaging, and conditional Herdr communication, the source repository's `docs/guides/advanced-task-execution-and-communication.md` has examples; check the live harness before selecting a mode. The installed skill works without that guide.*

8.1 **Subagents & model tiering — coordinate approved plans in sub-agent mode, right-size the model, escalate fast.** For an approved multi-task plan, the main session coordinates scoped subagents for separable implementation lanes and independent reviews; name each lane's owner, files, deliverable, and integration boundary. Reach for subagents whenever work decomposes cleanly: independent pieces that can run in parallel, or large sub-tasks better kept out of the main session's context. This never overrides execution order — work that is sequential by workflow, or that shares code/files, stays sequential; only genuinely independent work runs in parallel. **Don't over-delegate, either:** if briefing and dispatching a subagent would cost more than just doing the task inline, do it inline — spawn overhead and orchestration tokens aren't free. If the harness offers no subagents, say so and execute the approved plan sequentially; never claim a lane ran when it did not.

    **The roster is `references/roster.md`, beside this file — read it before dispatching.** It owns the **selection**: what makes a configuration a **Top**, **Strong**, **Standard** or **Fast** one — a model *and* a reasoning effort — the optional second family, and the dated binding of tiers to what your runtime actually offers; `codex-playbook-reviews` reads the same file. **This rule owns the assignments** — which tier does which work — and rule 3.1 owns which review runs on which tier. Model names change; the rules name tiers.

    - **Use the lowest capable configuration for the actual decision.** Fast is for mechanical, fully specified implementation; Standard for ordinary implementation and coordination; Strong for difficult integration or reasoning. Routine task decomposition, naming and applying an existing design stay with the capable coordinator. Use Top for a substantial new architecture, an unresolved high-impact design decision, or a planning consultation beyond the coordinator's demonstrated ability. Do not create a planner session just to restate an already specified task. Explicit owner bindings and role restrictions still apply; never silently change the running model.
    - **Difficulty, not a filename, determines escalation.** Complex security/trust-boundary design, concurrency invariants, memory safety and unsafe code start on Strong or a stronger allowed implementation configuration. A spelling change in Rust or a documentation edit beside authentication code does not acquire that floor merely by location. Security safeguards and required review remain unchanged. Increase reasoning effort for a bounded hard question; raise the model tier when capability is the limit. Maximum effort is not the default for status collection or dispatch.
    - **Review is not implementation, and it does not follow the same floor.** Mechanical review runs on **the Standard tier**, or on a configuration the roster qualifies for the mechanical review seat — never an unqualified Fast one, a conservative floor whose measurement and limits are in the roster — and deep review runs on the **Strong** tier (rule 3.1). An unqualified Fast configuration is thorough enough to be useful and not thorough enough to be a safety net.
    - **Escalate with evidence, not repeated briefs.** Every brief includes: "If blocked after a substantive attempt, return ESCALATE with the failed hypothesis, evidence, partial artifact and next useful diagnostic; do not loop or guess." Apply rule 7.2's two-attempt bound across replacements. Identify whether the cause is model capability, missing input, environment or a bad plan. Change models only for capability; unavailable disk or a broken command does not improve on a larger model. Carry previous evidence forward. Escalate Fast → Standard → Strong → Top only where the role permits it; at the allowed ceiling, report the blocker rather than repeat the attempt. Top remains planning/review-only where the owner's binding says so.
    - **Concurrency follows useful independence.** Start with at most two implementation workers; increase only for named independent deliverables that the coordinator can integrate and validate, within the runtime's slot limit. Review seats count toward that limit too. Local CPU count is not a reason to spawn cloud reasoning agents. Separately measure host load, available memory and disk before local heavy steps under rule 9.7; default to one heavy build/test writer until measured headroom supports more. Queue the rest. A lane's own commands obey the same admission rules.
    - **Keep one coordinator accountable.** The main session owns scope, task state, integration, stall detection and user updates. A planning consultation returns a design to that coordinator; do not require a new session or handoff just because the main session uses a strong model. Keep small tightly coupled edits inline when delegation costs more than it saves. For separable work, send a compact brief with exact files, dependencies, candidate, acceptance, permitted commands, progress checkpoint and handback format. Tell workers they share the repository and must preserve other edits. Prefer focused context over full-history forks when supported; include all applicable constraints. No recursive fan-out unless the coordinator explicitly assigns it.
    - **Wait for events without polling theater.** Register native completion/failure notifications and do independent authorized work. If a wait is needed, use a bounded event wait up to the harness's responsiveness limit (normally 60 seconds); do not immediately repeat short waits or print identical "still waiting" updates. Inspect status at the promised checkpoint or on a failure signal. Mandatory progress updates state observed work, blocker and next decision. A wait timeout is neither agent failure nor completion. The UI may render tool-call cards; rules can reduce unnecessary calls but cannot suppress client-generated cards.
    - **Know what actually contains a subagent, and don't confuse the controls.** An isolated working directory is **not** a sandbox. A worktree isolates *files in one repository*. A process sandbox limits *what the process can do*. A permission set limits *which actions are allowed*. They are three different controls, and only the ones your setup genuinely implements are real — an advertised capability is not evidence that it is enforced. Never describe one as another, and never widen what a subagent may do on the assumption that something else is holding the line.
    - **Scope & overrides.** This whole rule governs *ad-hoc* subagents you dispatch yourself. It does **not** apply to a purpose-built orchestration workflow with its own model and concurrency logic — when I invoke one of those, I mean it. And the model floor is for quality, never a cap on it: I can override **upward** anytime — name a stronger model, or freeze all work on a higher tier — and you hold that for the rest of the session until I lift it.
